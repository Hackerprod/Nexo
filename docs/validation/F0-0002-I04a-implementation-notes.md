## Alcance y archivos

`src/ir/model.rs` define las identidades mínimas, slots, temporales, bloque básico, instrucciones tipadas, procedencias, accesos, efectos propios y plan de limpieza. La identidad pública `FunctionId` es el nombre cualificado (en I04a, el nombre de módulo único); `table_index` es solo la posición canónica por nombre y puede variar cuando cambian otras funciones. La sustitución de desarrollo compara identidad y firma; el hash FNV-1a 64 codifica el contenido sin spans, índice ni orden de otras declaraciones. `src/ir/lower.rs` baja el AST normalizado de I02b después de `check::check_proposed`, en un hilo de 16 MiB con error interno controlado si el hilo no puede crearse. `src/ir/verify.rs` comprueba antes de ejecutar referencias, tipos, vida única de temporales, escrituras, efectos propios, procedencias, tabla explícita de ámbitos y padres, origen único, spans dentro de la fuente, plan de limpieza, terminador y hash. La IR tiene un bloque lineal por función en este subpaso; CFG general, préstamos y efectos transitivos esperan I06–I09.

`src/interp/machine.rs` ejecuta únicamente `Program` verificado, resuelve `main` desde la tabla, usa aritmética `i64` comprobada, valores escalares, bindings, sombreado, asignación completa, comparaciones y las primitivas escalares `print`, `assert_eq`, `drop` de datos y `fail`. La salida vive en `src/interp/observation.rs`: un registro ordenado con payloads, canales, LF virtual, bytes emitidos y reservas exactas preparadas para cierres posteriores. `src/ir/tests.rs` contiene las pruebas de fuente y el oráculo decimal independiente. `src/lib.rs` exporta los módulos aislados. No se cambiaron `frontend`, `check`, `diagnostic`, `runtime`, `syntax`, `main`, corpus, baseline ni ADR.

`compile`, `nexo check` y `nexo run` conservan el comportamiento anterior. `compile_scalar` devuelve `Rejected` para diagnósticos del frontend y checker; `OutsideScalarSlice` para capacidad posterior; `InvalidIr` se reserva para un defecto interno. Una escritura a `let` espera la etapa de propiedad de I04b, por lo que el API aislado no la ejecuta ni inventa NX-E0105. La IR inválida no adquiere un código de error de programa.

## Lagunas, límites y trabajo posterior

El ADR §14 usa offsets de corpus migrado con comentarios de códigos nuevos y saltos LF, mientras los archivos locales conservan comentarios antiguos y CRLF. La tabla espera `[45,64)` para el literal y `[33,40)` para `ignored`; el árbol de trabajo presenta `[42,61)` y `[31,38)`. `adr_gap_unmigrated_corpus_comments_and_crlf_keep_worktree_byte_offsets` fija el estado observable de esos bytes sin alterar el corpus heredado. El cierre de migración de corpus corresponde a I11.

La lectura literal de §17 restringe esta ejecución a datos escalares. Arrays, copias profundas, índices y escritura indexada corresponden a I04b; llamadas Nexo y recursos a I05; préstamos a I06; CFG, ramas y bucles a I07; Result y `?` a I08; efectos transitivos a I09; totales y fronteras completas de cuotas a I10; entrada mock y CLI ampliada a I11. El API actual aplica fronteras unitarias de trabajo, celdas y observación donde son alcanzables, pero no acredita las recetas completas de §11.3 ni los totales 56/25/15 de §11.7. Los planes de limpieza escalares son explícitos; las reservas de cierre esperan recursos.

Límites nominales: `work_consumed` aún difiere del modelo §11.6 (`fn main(){}` cuesta 3 y allí dice 2; I10); `let x=1;drop(x);print(x);` todavía se acepta (NX-E0202 corresponde a I05); el límite `ir_items` de 262.144 se completa en I10a. El hash usa equivalencia alfa y omite bloques sin efecto semántico: `{print(2);}` y `print(2)` tienen el mismo hash.

La tabla de §17.2 asigna el positivo completo de L07 al grupo I04, pero la fila de I04 especifica I04b para su cierre; aquí solo se acredita la ejecución escalar de bindings. No se declara una fase aprobada ni se adelantan las obligaciones de I04b.
